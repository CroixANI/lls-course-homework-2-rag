## 1. Hybrid Search (BM25 + Vector)

### Что такое BM25?

BM25 (Best Match 25) — это **алгоритм полнотекстового поиска по ключевым словам**, который является улучшенной версией TF-IDF. Думай о нём как о продвинутом `LIKE '%keyword%'` из SQL, но с учётом статистики.

**Как работает BM25:**
- Считает, как часто слово встречается в документе (TF — term frequency)
- Учитывает, насколько слово редкое во всей базе документов (IDF — inverse document frequency)
- Штрафует слишком длинные документы (чтобы большие файлы не выигрывали только за счёт объёма)

**Аналогия из C#:** Представь, что у тебя есть `Dictionary<string, List<int>>`, где ключ — слово, а значение — список ID документов, в которых оно встречается. BM25 — это математическая формула оценки релевантности на основе такого инвертированного индекса.

### Что такое векторный поиск (Vector Search)?

Это **то, что уже есть в текущем коде**. Текст переводится в числовой вектор (embedding), и поиск происходит по близости векторов в многомерном пространстве.

**Аналогия:** Если BM25 ищет по буквальному совпадению слов, то векторный поиск понимает смысл. Запрос «автомобиль» найдёт документы со словом «машина», потому что их векторы близки.

### Проблема одного метода

| Ситуация | BM25 | Векторный поиск |
|---|---|---|
| Запрос «403 Forbidden» | Найдёт точный код ✅ | Может найти «ошибки доступа» вместо точного кода ❌ |
| Запрос «проблемы с входом» | Не найдёт «authentication error» ❌ | Найдёт по смыслу ✅ |

**Вывод:** Нужны оба метода вместе.

### RRF — Reciprocal Rank Fusion

Это алгоритм **слияния двух списков результатов** в один. Задача: получить список из BM25 и список из FAISS, объединить их честно.

**Как работает RRF:**

Для каждого документа считается итоговый балл:

```
RRF_score(doc) = 1 / (k + rank_bm25) + 1 / (k + rank_vector)
```

Где:
- `rank_bm25` — позиция документа в списке BM25 (1-й, 2-й, 3-й...)
- `rank_vector` — позиция в списке векторного поиска
- `k` — константа (обычно 60), сглаживающая влияние топ-результатов

**Пример на Python-псевдокоде:**
```python
def rrf_merge(bm25_results, vector_results, k=60):
    scores = {}
    for rank, doc_id in enumerate(bm25_results, start=1):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    for rank, doc_id in enumerate(vector_results, start=1):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

**Альтернатива — Weighted Sum:** Просто перемножить баллы на веса: `score = 0.5 * bm25_score + 0.5 * vector_score`. Проще, но требует нормализации шкал обоих методов.

### Как это соотносится с текущим кодом

Текущий код в `src/rag/query.py`:

```python
# query.py, строка 86-89 — только векторный поиск
q_emb = model.encode([query])
faiss.normalize_L2(q_emb)
scores, ids = index.search(q_emb, TOP_K)  # ищет только в FAISS
```

**Что нужно добавить:**
- Создать BM25-индекс из тех же `chunks` (список словарей с полем `"text"`), которые уже загружены в `query.py`
- Запустить BM25-поиск параллельно с FAISS-поиском
- Объединить результаты через RRF
- В `config.py` добавить `TOP_K = 20` для гибридного поиска (перед реранкингом)

**Библиотека для BM25:** `rank_bm25` — простая, легко устанавливается через `pip`.

## 2. Reranking (Cross-Encoder)

### Архитектура: Bi-Encoder vs Cross-Encoder

Текущий код использует **Bi-Encoder** (двойной энкодер):
- Запрос → вектор
- Каждый документ → вектор (заранее, при индексировании)
- Сравниваются векторы (cosine similarity)

**Это быстро**, но менее точно, потому что запрос и документ обрабатываются **отдельно**.

**Cross-Encoder** работает иначе:
- Запрос + документ → подаются **вместе** в модель
- Модель видит взаимосвязи между словами запроса и документа
- Выдаёт один балл релевантности

**Аналогия из жизни:**  
Bi-Encoder — это резюмировать каждый документ отдельно, а потом сравнивать резюме с резюме запроса.  
Cross-Encoder — это читать документ, держа вопрос в голове, и сразу оценивать «отвечает ли этот текст на вопрос?»

### Почему Cross-Encoder нельзя использовать с самого начала?

Cross-Encoder **медленный**: он должен обработать каждую пару (запрос, документ). Если у тебя 10 000 чанков — это 10 000 запросов к модели. Это займёт секунды или минуты.

**Поэтому используется двухэтапная схема:**
1. **Быстрый отбор** (Bi-Encoder/FAISS + BM25) → Top-20 кандидатов
2. **Точная оценка** (Cross-Encoder) → Top-5 из 20-ти

### Модель BAAI/bge-reranker-base

`BAAI/bge-reranker-base` — это лёгкая модель реранкинга от Пекинской академии ИИ. Она:
- Весит ~278 МБ
- Работает локально через библиотеку `sentence-transformers` или `FlagEmbedding`
- Принимает пары (запрос, текст) и возвращает скор от 0 до 1

**Пример использования:**
```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-base")

# query — запрос пользователя, top20_chunks — список из 20 чанков
pairs = [(query, chunk["text"]) for chunk in top20_chunks]
scores = reranker.predict(pairs)

# Сортируем по убыванию скора и берём топ-5
ranked = sorted(zip(scores, top20_chunks), key=lambda x: x[0], reverse=True)
top5 = [chunk for _, chunk in ranked[:5]]
```

### Как это соотносится с текущим кодом

Текущий `retrieve()` в `query.py` возвращает `TOP_K = 5` результатов напрямую из FAISS.

**Что нужно изменить:**
1. В `config.py` добавить `TOP_K_HYBRID = 20` и `TOP_K_RERANK = 5`
2. Гибридный поиск возвращает 20 чанков
3. Реранкер пересортировывает их и возвращает 5

```python
# Было (query.py, строка 97):
return [chunks[i] for i in ids[0]]  # возвращает TOP_K результатов

# Станет (концептуально):
candidates = hybrid_search(query, top_k=20)   # шаг 1: быстрый отбор
reranked = rerank(query, candidates, top_k=5) # шаг 2: точная фильтрация
return reranked
```

### Рекомендация по коду

Функцию `retrieve()` стоит разбить на три отдельные функции:
- `hybrid_retrieve(query, top_k)` — гибридный поиск (BM25 + Vector)
- `rerank(query, candidates, top_k)` — реранкинг через Cross-Encoder
- `retrieve(query)` — основная функция, которая вызывает первые две (так не сломается `ask()` в строке 150)

## 3. Query Expansion (LLM Rewrite)

### Что такое расширение запроса?

Query Expansion — это **предобработка запроса пользователя** перед тем, как его отправить в поисковую систему.

**Проблема:** Пользователи пишут короткие или нечёткие запросы:
- `sqli` → система не знает, что это SQL Injection
- `403` → неясно, это HTTP-код или что-то другое
- `не могу войти` → слишком расплывчато для точного поиска

**Решение:** Попросить LLM «улучшить» запрос перед поиском.

### Три подхода к Query Expansion

**1. HyDE (Hypothetical Document Embedding)**  
LLM генерирует **гипотетический ответ** на запрос, и уже этот ответ используется для поиска.
```
Запрос: "sqli"
HyDE: "SQL Injection — это атака, при которой..."  ← используется для поиска
```

**2. Query Rewriting (то, что в задании)**  
LLM переформулирует запрос, делая его более конкретным и полным.
```
Запрос: "sqli"
Rewrite: "SQL Injection vulnerability examples and prevention"
```

**3. Multi-Query**  
LLM генерирует несколько вариантов запроса, поиск идёт по всем, результаты объединяются.
```
Запрос: "проблемы с входом"
→ "ошибка аутентификации"
→ "login failed error"  
→ "authentication issue troubleshooting"
```

### Когда расширять запрос?

В задании указано два условия:
- Запрос **слишком короткий** (например, 1-2 слова)
- Запрос **содержит аббревиатуры** (sqli, csrf, xss, rbac...)

Это можно определить простой проверкой перед поиском.

### Как это реализуется

LLM уже есть в проекте — Ollama с моделью `qwen3:0.6b`. Для расширения запроса нужно отправить в него специальный системный промпт:

```python
def expand_query(query: str) -> str:
    """Расширить запрос, если он слишком короткий или содержит аббревиатуры."""
    words = query.strip().split()
    is_short = len(words) <= 2
    # Список известных аббревиатур можно вынести в config.py
    known_abbrevs = {"sqli", "xss", "csrf", "rbac", "iam", "sso", "2fa", "mfa"}
    has_abbrev = any(w.lower() in known_abbrevs for w in words)

    if not (is_short or has_abbrev):
        return query  # запрос нормальный, расширение не нужно

    prompt = f"""You are a search query expander. 
Expand the following short or abbreviated query into a more descriptive search phrase.
Return ONLY the expanded query, nothing else.

Query: {query}
Expanded query:"""

    expanded = ask_llm(prompt).strip()
    print(f'[QueryExpansion] "{query}" → "{expanded}"')
    return expanded
```

### Как это соотносится с текущим кодом

Функция `ask()` в `query.py` (строка 148-152) — точка входа для ответа на вопрос:

```python
# Было (query.py, строки 148-152):
def ask(query: str):
    """Answer a question using RAG."""
    contexts = retrieve(query)
    prompt = build_prompt(query, contexts)
    return ask_llm(prompt), contexts

# Станет (концептуально):
def ask(query: str):
    """Answer a question using RAG."""
    expanded_query = expand_query(query)   # шаг 0: расширение запроса
    contexts = retrieve(expanded_query)    # шаг 1: поиск по расширенному запросу
    prompt = build_prompt(query, contexts) # в промпте — оригинальный запрос!
    return ask_llm(prompt), contexts
```

**Важно:** В `build_prompt()` передаётся **оригинальный** запрос пользователя, а не расширенный. Расширение нужно только для поиска — пользователь должен видеть ответ на свой вопрос, а не на переформулированный.

### Рекомендации по коду

1. Вынести список аббревиатур в `config.py` как `KNOWN_ABBREVS = {...}` — проще расширять
2. Логировать оба запроса: исходный и расширенный (уже есть паттерн `[RAG]` в `query.py`)
3. Добавить `QUERY_MIN_WORDS = 2` в `config.py` как порог для расширения

## Итоговая схема улучшенного пайплайна

```
Запрос пользователя
        │
        ▼
┌─────────────────┐
│  Query Expansion │  ← Пункт 3: расширить если короткий/аббревиатура
│  (LLM Rewrite)  │
└────────┬────────┘
         │ расширенный запрос
         ▼
┌─────────────────────────────────┐
│         Hybrid Search           │  ← Пункт 1: параллельный поиск
│  ┌──────────┐  ┌─────────────┐  │
│  │  BM25    │  │ FAISS/Vector│  │
│  │ (новое)  │  │ (текущий)   │  │
│  └────┬─────┘  └──────┬──────┘  │
│       └───────┬────────┘         │
│            RRF Merge             │
│         (Top-20 results)         │
└───────────────┬─────────────────┘
                │ 20 кандидатов
                ▼
┌─────────────────────────────────┐
│      Cross-Encoder Reranker     │  ← Пункт 2: точная оценка
│      (BAAI/bge-reranker-base)   │
│         → Top-5 results         │
└───────────────┬─────────────────┘
                │ 5 лучших чанков
                ▼
┌─────────────────────────────────┐
│           LLM (Ollama)          │  ← существующий код (ask_llm)
│       build_prompt + answer     │
└─────────────────────────────────┘
```
