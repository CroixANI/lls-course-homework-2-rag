# Анализ потока данных в методе поиска (Impact Analysis)

## ASCII-диаграмма потока данных

```
Пользователь
    │ query: str  (stdin)
    ▼
src/main.py → main()
    │ query: str
    ▼
src/assistant.py → CompanyKBAssistant.query(user_query)
    │
    ├──────────────────────────────────────────────┐
    │  [Шаг 1: RAG Retrieve]                       │
    ▼                                              │
src/rag/query.py → retrieve(query)                │
    │                                              │
    │  1. model.encode([query])                    │
    │     SentenceTransformer("all-MiniLM-L6-v2")  │
    │     query: str  →  q_emb: ndarray[1, 384]    │
    │                                              │
    │  2. faiss.normalize_L2(q_emb)                │

    │     → scores: ndarray[1,5]  (dot-product)    │
    │     → ids:    ndarray[1,5]  (индексы чанков) │
    │                                              │

    │     → contexts: List[Dict]                   │

    │         "chunk_id": int }                    │

    ◄──────────────────────────────────────────────┘

src/assistant.py → _llm_decide_mcp_usage()        │
    │                                              │
    │  ollama.Client().chat(model, decision_prompt)│

    │                                              │

    │    │ src/mcp/client.py → call_tool()  │      │

    │    │   ▼                              │      │

    │

    │                                              │
    │  context_text = join([                       │
    │    f"[Source: {c['source']}]\n{c['text']}"   │
    │    for c in contexts                         │

    │  → prompt: str  (XML-структура)              │
    │                                              │
    │  if mcp_result:                              │
    │    prompt += <additional_info_from_mcp_tool> │
```

## Пошаговое описание

### Шаг 0 — Инициализация индекса (однократно при запуске)

**Файл:** `src/rag/query.py:_ensure_index_exists` (строки 26–69)

| | |
|---|---|
| **Вход** | нет — вызов при импорте модуля |
| **Выход** | глобальные `index: faiss.IndexFlatIP`, `chunks: List[Dict]` |
| **Что происходит** | Читает `index.faiss` (FAISS-индекс, тип `IndexFlatIP` — inner product) и `chunks.pkl` (сериализованный список словарей). Если файлов нет — вызывает `build_index()`. Индекс хранит L2-нормализованные эмбеддинги размерности 384. |

---

### Шаг 1 — Кодирование запроса в эмбеддинг

**Файл:** `src/rag/query.py:retrieve` (строка 86–87)

| | |
|---|---|
| **Вход** | `query: str` — вопрос пользователя на естественном языке |
| **Выход** | `q_emb: numpy.ndarray` формы `[1, 384]` |
| **Что происходит** | `SentenceTransformer("all-MiniLM-L6-v2").encode([query])` — модель превращает текст в плотный вектор 384-измерений. Затем `faiss.normalize_L2(q_emb)` — вектор нормализуется до единичной длины, чтобы dot-product стал эквивалентен cosine similarity. |

---

### Шаг 2 — Поиск по FAISS-индексу

**Файл:** `src/rag/query.py:retrieve` (строка 89–90)

| | |
|---|---|
| **Вход** | `q_emb: ndarray[1, 384]`, `TOP_K=5` |
| **Выход** | `scores: ndarray[1, 5]` — значения схожести; `ids: ndarray[1, 5]` — индексы чанков |
| **Что происходит** | `index.search(q_emb, TOP_K)` ищет 5 ближайших векторов методом полного перебора (IndexFlatIP). `scores` — значения inner product (от -1 до 1 после нормализации). `ids[0]` — позиции найденных чанков в массиве `chunks`. |

> **Важно:** `scores` после `retrieve()` **полностью отбрасываются** — возвращается только `[chunks[i] for i in ids[0]]`.

---

### Шаг 3 — Формирование контекста из чанков

**Файл:** `src/rag/query.py:retrieve` (строка 90), `src/rag/chunk.py:chunk_documents`

| | |
|---|---|
| **Вход** | `ids[0]: ndarray[5]` — индексы |
| **Выход** | `contexts: List[Dict]` — список из `{"text": str, "source": str, "chunk_id": int}` |
| **Что происходит** | Прямая индексация в глобальный список `chunks`. Каждый чанк — фрагмент документа размером до 700 токенов с перекрытием 100 токенов, нарезанный через `tiktoken` (cl100k_base). |

---

### Шаг 4 — Решение об использовании MCP (второй LLM-вызов)

**Файл:** `src/assistant.py:_llm_decide_mcp_usage` (строки 35–107)

| | |
|---|---|
| **Вход** | `query: str`, `contexts: List[Dict]` |
| **Выход** | `(tool_name: str|None, tool_args: dict|None)` |
| **Что происходит** | Через `ollama.Client().chat()` (API отличается от `ask_llm`!) отправляется decision-промпт. LLM возвращает JSON с решением. Если `use_mcp=true` — вызывается нужный инструмент через subprocess JSON-RPC. |

---

### Шаг 5 — Построение финального промпта

**Файл:** `src/rag/query.py:build_prompt` (строки 93–125)

| | |
|---|---|
| **Вход** | `query: str`, `contexts: List[Dict]` |
| **Выход** | `prompt: str` — XML-структурированный промпт |
| **Что происходит** | Чанки объединяются через `\n\n`, каждый предваряется `[Source: <path>]`. Формируется XML-шаблон с `<role>`, `<instructions>`, `<context>`, `<query>`. Если `mcp_result` есть — в `assistant.py` к промпту дописывается тег `<additional_info_from_mcp_tool>`. |

---

### Шаг 6 — Генерация ответа (Ollama)

**Файл:** `src/rag/query.py:ask_llm` (строки 128–138)

| | |
|---|---|
| **Вход** | `prompt: str` |
| **Выход** | `answer: str` |
| **Что происходит** | HTTP POST на `localhost:11434/api/generate` с `stream: false`. Ответ — `response.json()["response"]`. Используется модель `qwen3:0.6b`. |

---

### Шаг 7 — Сборка ответа и возврат в main

**Файл:** `src/assistant.py:query` (строки 152–158)

| | |
|---|---|
| **Вход** | `answer: str`, `contexts: List[Dict]` |
| **Выход** | `Dict {"answer", "sources", "mcp_used", "mcp_tool"}` |
| **Что происходит** | `sources = [c["source"] for c in contexts]` — список путей к файлам. Дубликаты удаляются только на уровне вывода в `assistant.py` (`seen_sources`), но не в `main.py`. |

## Потенциальные проблемы и узкие места

### 1. `scores` полностью теряются после FAISS-поиска
**Где:** `src/rag/query.py:90` — `return [chunks[i] for i in ids[0]]`

Значения релевантности (`scores`) отбрасываются. Это значит:
- Нельзя отфильтровать нерелевантные результаты по порогу (например, `score < 0.3`)
- LLM получает 5 чанков независимо от того, насколько они близки к запросу
- Нет возможности ранжировать источники по релевантности в ответе

---

### 2. Два разных клиента для Ollama
**Где:** `ask_llm` использует `requests.post` (HTTP), а `_llm_decide_mcp_usage` использует `ollama.Client().chat()` (SDK)

Это две независимые точки интеграции с одним и тем же сервисом — дублирование, разное поведение при ошибках.

---

### 3. Отсутствует фильтрация дубликатов источников в `main.py`
**Где:** `src/main.py:46–48`

В `assistant.py` при прямом запуске дубликаты фильтруются через `seen_sources`, но в `main.py` этой логики нет — один файл может появиться в списке источников несколько раз.

---

### 4. `chunk_id` не используется при поиске
**Где:** `src/rag/chunk.py:36`, `src/rag/query.py:retrieve`

Каждый чанк хранит `chunk_id` (порядковый номер внутри документа), но это поле нигде не используется. Соседние чанки не подтягиваются даже если совпал только средний — контекст может быть обрезан по границе чанка.

---

### 5. MCP security check сломан
**Где:** `src/mcp/server.py:18`

```python
if not str(path.resolve()).startswith(str(Path(DOCUMENTS_DIR).resolve())):
```

`DOCUMENTS_DIR = "./docs"` — относительный путь. `Path("./docs").resolve()` вычисляется относительно CWD процесса MCP-сервера, который запускается с `cwd=Path(__file__).parent.parent` (каталог `src/`). Если `docs/` находится не там — проверка будет неверной.

---

### 6. Нет обработки `ids == -1` из FAISS
**Где:** `src/rag/query.py:90`

Если индекс содержит меньше `TOP_K` документов, FAISS вернёт `-1` в `ids[0]`. `chunks[-1]` вернёт последний элемент списка, а не ошибку — тихая ошибка с неверными результатами.
